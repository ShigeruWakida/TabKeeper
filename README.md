# TabKeeper

Chrome Manifest V3拡張機能。現在の**1ウィンドウ**のタブURL・並び順・固定状態・選択タブをJSONに保存し、新しいウィンドウへ復元します。

## v1.1.1 の変更点

- ポップアップを専用の操作タブに変更し、フォルダー選択中も画面と非同期処理を維持
- 操作タブ自身は保存対象から除外し、アイコンを押す直前のタブをアクティブタブとして記録（そのタブが閉じられた場合は先頭タブ）
- 同じウィンドウでは操作タブを再利用し、複数画面からの保存はWeb Locksで直列化
- 初回に「保存先フォルダーを選択・変更」でフォルダーを指定し、そのフォルダーのハンドルをIndexedDBに記憶
- 以後は同じフォルダーへ直接保存（Chromeの権限が失効した場合、保存時に再許可が必要）
- 保存名はローカル日時の秒までを使う `TabKeeper-YYYYMMDD-HHMMSS.json`
- 同じ秒にファイル名が重複した場合、`-001`、`-002`…を付けて既存のバックアップを上書きしない
- ChromiumのFile System Access API（`showDirectoryPicker`）が必要。Chromeの設定・ポリシーによっては使えない場合があります

## 操作

1. Chromeで `chrome://extensions` を開き、デベロッパーモードをオンにします
2. このリポジトリをダウンロード・展開し、`manifest.json` のあるフォルダーを「パッケージ化されていない拡張機能を読み込む」で選びます
3. 保存したいウィンドウでTabKeeperのアイコンを押し、開いた操作タブで「保存先フォルダーを選択・変更」で保存先を指定します
4. 「現在のタブをJSONに保存」でバックアップします
5. 復元は従来どおりJSONファイルを選択して「新しいウィンドウに復元」を押します

## 制限事項

- 保存先フォルダーの**名前**を表示します。ブラウザーの仕様により絶対パスは取得しません
- プロファイルを変更・削除した場合、拡張機能の保存情報が消えた場合、フォルダーが移動・削除された場合には再設定が必要です
- `http://` / `https://` 以外のURL（`chrome://`、`file://` 等）はJSONに含まれても復元時にスキップします
- タブグループ、複数ウィンドウ、フォーム入力内容、スクロール位置、ログイン情報は保存・復元しません
- JSONには個人的なURLが含まれます。公開リポジトリへアップロードしないでください

## テスト

`node --test tests/*.test.cjs`

## 更新・ZIP導入

- 初回: ZIPを固定のフォルダーへ展開し、その中の `manifest.json` があるフォルダーを読み込みます。
- 既存版から更新: 操作画面を閉じ、既に読み込んでいるフォルダーの拡張機能ファイルを新版で更新し、`chrome://extensions` でTabKeeperの再読み込みボタンを押してください。表示が1.1.1になったことを確認します。
- 保存先情報を引き継ぐには、同じChromeプロファイル・拡張機能IDを維持してください。削除して再登録したり、別の展開先を新規登録すると引き継げない場合があります。
- IndexedDBのDB名 `tabkeeper-settings`、store `settings`、key `directory` はv1.1.0から変更していません。
- Chrome再起動後も保存先ハンドルを読み込みます。書き込み許可は別管理です。再許可が必要と表示されたら「現在のタブをJSONに保存」を押し、Chromeの確認画面で許可してください。フォルダーの選び直しは原則不要です。
- 保存先が移動・削除された、アクセス権がなくなった、ドライブが外れた場合はエラーを表示します。接続・権限を確認するか「保存先フォルダーを選択・変更」で再設定してください。
- 開いた操作タブのあるウィンドウだけを保存します。操作タブを別ウィンドウへ移動すると、その移動先が保存対象になります。

## 原因調査

確認した実装: v1.1.0では `action.default_popup` で開く画面の中で、選択ダイアログ待機→IndexedDB保存→JSON保存を実行していました。

Chrome公式仕様では、ポップアップは外部へのフォーカス移動で閉じます。この寿命の短い画面に選択後の非同期処理を置いていたことが設計上の不具合です。ユーザー申告の症状と整合しますが、今回の環境でポップアップ破棄の実機ログは取得していないため、実機の直接原因としては未確定です。専用タブでこの中断経路を取り除きました。

| 調査事項 | 結果 |
|---|---|
| popup内の `showDirectoryPicker()` | APIの存在と処理完了は別問題。popup内での完了を保証できず、専用タブからクリック直後に呼ぶ構成に変更 |
| フォルダー選択時のpopup破棄 | フォーカス移動時に閉じる仕様を確認。今回の実機挙動は未検証 |
| ハンドルのIndexedDB保存・再取得 | 公式に対応。既存のDB構造を維持し、書き込みtransaction完了を待機 |
| 再起動後の権限 | ハンドル保持とは独立。起動時と保存時に `queryPermission({mode:'readwrite'})` で確認 |
| `requestPermission()` の条件 | ユーザー操作が必要。保存ボタンの処理で、タブ取得やファイル書き込みより先に要求 |
| 拡張機能更新 | 同一ID・プロファイルの同じoriginのIndexedDBを再利用する設計。実更新による保持は実機確認待ち |
| MV3権限 | URL取得用の `tabs` のみ。File System Accessはユーザー許可で利用し、追加のhost権限や外部通信は不要 |

- [File System Access API: ハンドル保存・権限・ユーザー操作](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)
- [永続的な許可と再許可](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api)

## 検証結果とChrome実機確認手順

自動テストは `node --test tests/*.test.cjs`。セッション形式・日時・連番・既存内容保持・アクセスエラー・失敗時のstream中止、API模擬によるフォルダー選択/変更/再読込/連続保存/復元を確認します。v1.0.0タグの実装とJSONスキーマが同じことも確認しました。模擬テストは本物のIndexedDBによるハンドル直列化やChrome再起動の証明ではありません。

以下はすべてChrome実機では未検証です。正式Release前に確認してください。

1. 複数のHTTP(S)タブを開き、一部をピン留めし、選択タブを決めてTabKeeperを起動する。
2. 初回フォルダー選択後、画面が残り「記憶しました」と表示されることを確認し、保存する。
3. JSONのURL・順序・pin・activeと、ローカル秒単位のファイル名を確認する。操作タブが含まれないことを確認する。
4. 連続保存する。同秒の保存または既存の同名ファイルで `-001`、`-002` が付き、元の内容が変わらないことを確認する。
5. Chromeを全終了して再起動し、保存先名が復元されることを確認する。必要時は保存ボタンで再許可し、選び直さず保存できることを確認する。
6. 保存先を変更し、新しい保存先だけに保存されることを確認する。選択キャンセル時は元の設定が残ることを確認する。
7. 書き込み許可の拒否・フォルダー削除・ドライブ切断等で明確なエラーが表示され、再選択で復旧できることを確認する。
8. 今回のJSONとv1.0.0のJSONを選択して復元し、新しいウィンドウの順序・ピン留め・選択タブが一致し、既存ウィンドウが残ることを確認する。
9. 同じ読み込み先・IDのv1.1.0から更新し、保存先が保持されることを確認する。

他のアプリが存在確認と作成の間に全く同じ名前を作成する競合はFile System Access APIで原子的に排除できません。TabKeeper間の保存は同一originのWeb Locksで直列化します。
